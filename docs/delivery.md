## 推理效率

### 表格设计的基本逻辑

效率表要让读者判断：**同一种任务、同一交付质量和可比资源条件下，哪个方案快了多少、绝对耗时是多少、资源和成本付出了什么代价，结果能否复现。**

先分开写“优化策略”“测试条件”和“测量结果”，通过工况 ID / 方案 ID 关联。不要把配置藏在表外口头解释，也不要只列加速比。

1. 一种工况固定输入/输出规格、硬件、batch/并发和测试方法；每个工况都有自己的 baseline。480P/5s 和 720P/15s 分别比较，不能拿不同任务的时间直接相除。
2. 每一行明确方案、代码/模型版本和开关。逐步叠加优化说明整体收益；同时打开多个开关不能证明其中某一个优化的独立贡献。声称单项收益时补单变量消融。
3. 先报带单位和统计口径的绝对时间，再报相对收益。延迟是响应速度，吞吐是批量产能；需要分别定义，不互相代替。
4. 蒸馏、少步、量化、缓存或上采样可能改变质量。效率与同一评测集上的质量结果一起给出。减少有效输入、输出帧数或改变画质条件时，明确这是另一种方案，不能直接宣称等质量加速。
5. 成本必须有分母和计费假设。元/视频、元/生成视频秒、元/推理计算秒是不同指标；同时标出绝对成本与相对变化。
6. 每组数字关联原始计时记录、参数和固定版本。未测用“未测”，证据不足用 UNKNOWN，计算不适用用“—”；不能将空值变成 `0`。

### 必备要素

必备的是这些信息，不要求全部挤在一张宽表中。公共配置放在条件表，每行通过 ID 引用；变化的字段要回到对应方案行中。

| 要素 | 必须说清楚什么 | 缺失时无法判断什么 |
| --- | --- | --- |
| 方案与对照 | baseline、候选模型/代码 SHA、配置版本、精度和优化开关 | 到底比较了什么，能否复现 |
| 工作量 | 输入类型/长度/尺寸，输出宽×高、帧率、帧数/时长；实际内部计算尺寸也注明 | 是否通过减少任务量获得收益 |
| 资源环境 | GPU 型号与卡数、并行方式、CPU/驱动/框架版本、batch 和并发 | 是否只是换卡或增加资源 |
| 生成参数 | 主模型/上采样器步数、采样器、CFG、种子等影响计算或质量的参数 | 少步与其他优化贡献能否区分 |
| 计时边界 | 是否含加载、编译、预处理、主模型、解码、上采样、I/O、排队；GPU 异步执行如何同步 | 数字是模型局部时间还是可交付响应时间 |
| 统计方法 | 固定样本集/数量、预热次数、重复次数、统计量与波动；冷启动与稳态分开 | 是否只报最快一次、是否稳定 |
| 绝对结果 | 带单位的耗时、吞吐定义、峰值显存（注明每卡/整机） | 业务能否使用、资源是否能部署 |
| 相对结果 | 每种工况对应哪个 baseline，使用同一统计量计算加速比 | 加速比是否公平、可重算 |
| 质量与约束 | 同评测集效果、退化幅度、失败率/困难 case、验收阈值 | 是否牺牲质量换速度 |
| 成本与证据 | 卡费是单卡还是整机，币种、计费周期、利用率假设、计算公式、原始报告 | 成本是否重复乘卡数、数据是否可核验 |

统计至少给出样本数和重复方式，以及均值/中位数与波动（如 mean±std 或 p50/p95）；在线交付有尾延迟要求时必须报告对应分位数。成本估算优先采用平均资源占用时间，不能把最快一次或 p50 直接当作平均账单。

### 计算口径

设相同工况的 baseline 时间为 `T_base`，候选时间为 `T_candidate`；总墙钟时间 `T` 内生成 `m` 个、每个 `L` 秒的视频；所使用全部资源的计费速率为 `r` 元/计算秒。

```text
加速比 = T_base / T_candidate                 # 使用同一统计量与工作量
耗时降低比例 = 1 - T_candidate / T_base       # 不是“加速比 × 100%”
吞吐（视频/分钟）= 60 × m / T
吞吐（生成视频秒/计算秒）= m × L / T
成本（元/视频）= r × T / m
成本（元/生成视频秒）= r × T / (m × L)
```

月租折算必须写明一个月按多少秒计、卡数和利用率。若 `r` 已是四卡整机速率，就不能再乘四；比较不同卡数时分别计算各方案的 `r`。批量/并发运行使用实际总耗时和总产量，不把单视频时间直接当成服务吞吐。闲置、失败重试、训练、存储、网络等费用是否计入要明确，理想占满的资源成本不能直接宣称实际生产账单。

### 会被批评或要求重测的情况

| 问题写法 | 为什么不够 | 怎么改 |
| --- | --- | --- |
| 只写“19.91×”，没有绝对耗时 | 看不出实际等待多久，无法重算 | 同时写 baseline、候选时间、单位和统计口径 |
| 时间不标单位，`5s` 的生成内容时长被当作推理耗时 | 工作量与延迟混淆 | 输出时长和实际计算耗时分列 |
| 480P 与 720P、不同卡数/batch 或不同样本集直接相除 | 比较条件不同 | 固定工况，差异方案单列并说明资源代价 |
| 50→8 步、量化或上采样后只报速度，不报效果 | 没有证明蒸馏后仍满足质量要求 | 补同评测集质量、退化和 bad cases |
| 只报主模型时间，省略解码/上采样/加载，却称端到端 | 少算用户实际等待的阶段 | 明确计时边界，补完整链路或注明局部结果 |
| 同时启用量化和注意力优化，却把全部收益归给蒸馏 | 没有单变量证据 | 报整体收益；单项归因另做消融 |
| 只展示最快一次，不写样本数、重复、波动 | 无法判断结果的代表性 | 预热后对固定样本集统计，保留逐次记录 |
| 空耗时造成 `#DIV/0!`，成本显示 `0.000` | 未测被误写成零成本 | 未测传播为未测/UNKNOWN，不计算比值和成本 |
| 卡费含义不清，重复乘卡数，元/视频与元/生成秒混用 | 成本不能核验或比较 | 展示费率、公式、单位、计费主体和假设 |
| 没有代码 SHA、模型/配置版本和原始日志 | 他人无法重复测量 | 补全证据链，补齐前保留 UNKNOWN |

详细测评口径可引用 [eval.md](eval.md)，本节保留能独立读懂比较结论的必要信息。
