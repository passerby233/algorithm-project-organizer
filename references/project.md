## 节点记录约定

- **何时记录：** 作出已确认决策、执行关键操作、得到影响判断的实验结果、达成里程碑，或出现 / 解除阻塞时。普通调试无需逐条记录。
- **如何关联：** 节点编号使用 `N001`、`N002` 等并递增；记录前序节点和触发依据。并行工作可从同一节点分支，汇合时引用多个前序节点。
- **如何保留历史：** 实际变化发生后，在文件末尾追加节点，并同步索引与当前节点。旧节点保留当时的事实与状态；修正错误时注明原因，后续决策通过新节点说明替代关系。
- **事实与判断：** 操作完成、效果成立、里程碑通过分别提供证据。引用已有 EXP、评测报告、提交或确认记录；量化结果应能追溯到实际版本和测试条件。证据缺失写 `UNKNOWN`，未经确认的建议留在方案中。
- **待执行的含义：** 已经确认某项决定，但动作尚未落实。记录确认人和依据；详细执行计划仍写在 1-design.md，不预建未来节点或把预期收益当成成果。
- **上级介入：** 明确需要谁解决什么问题，例如资源协调、跨团队依赖、优先级或范围取舍。区分“需要介入”“已提出请求”“已获答复”，只记录真实发生的沟通和决定。

| 状态 | 含义 |
| --- | --- |
| 待执行 | 决定已确认，尚未开始落实 |
| 进行中 | 已开始执行，工作尚未结束 |
| 受阻 | 已发生的问题阻止继续推进 |
| 已完成 | 本次工作或里程碑有证据完成；实验结束仍需说明效果是否达标 |
| 已停止 | 已确认停止本项工作，保留原因和已有结果；停止不等于交付通过 |

## 节点填写格式

复制下面的模块到“实际节点记录”，替换占位内容。仅保留适用的事实项；每个节点都要回答变化、证据、状态、瓶颈 / 风险和上级介入情况。模板本身不计为实际进展。

```markdown
### Nxxx｜YYYY-MM-DD｜节点名称

- 类型：操作 / 实验结果 / 决策 / 里程碑 / 阻塞变化（可多选）。
- 发生时间 / 记录人：填写时间与时区、记录人。
- 来源与核验情况：对话陈述 / 原始记录 / 已核验结果；引用可定位的材料。时间未知时注明待补充，不将整理时间作为事件发生时间。
- 关联任务 / 实际负责人：引用 1-design.md 中的任务编号或名称，填写实际负责人。
- 前序节点：填写节点链接；首个节点写“无”。

#### 触发依据

什么已发生的决策、实验结果或外部变化触发了本节点？引用对应节点或证据。

#### 已发生的事实与变化

- 已执行操作：实际做了什么；仅作出决定时写“尚未执行”。
- 实际结果：相较前序节点，新增了什么能力、解决了什么问题或得到了什么结果。
- 已确认决策（涉及时）：选择了什么、主要备选及选择依据；确认人 / 日期 / 确认记录。
- 已实现里程碑（涉及时）：达成了什么要求、验收证据及确认人；未通过则如实记录。
- 证据：EXP、评测报告、实际提交、任务记录或确认记录的固定链接。

#### 节点发生时的状态

| 项目 | 记录 |
| --- | --- |
| 状态 | 待执行 / 进行中 / 受阻 / 已完成 / 已停止 |
| 瓶颈 | 已发生的障碍及其影响；无则写“无”，尚不清楚则写“待判断” |
| 风险 | 可能发生的问题、影响和已有依据；无则写“无”，尚不清楚则写“待判断” |
| 是否需要上级介入 | 不需要 / 需要 / 待判断 |
| 介入事项（需要时） | 需要哪位上级协调或决定什么、原因、影响和期望响应时间 |
| 实际介入情况（需要时） | 尚未提出请求 / 已提出请求（时间、记录）/ 已获答复（决定及确认人） |
| 已确认的待执行事项 | 已确认但尚未落实的动作及负责人；无则写“无”，详细计划引用 1-design.md |

后续发生新的操作、决定或状态变化时，追加新节点并引用本节点。
```
