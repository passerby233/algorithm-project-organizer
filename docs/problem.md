# 问题定义与验收

负责人、当前指标和期限见 [project.yaml](../project.yaml)。本文件保存问题边界和验收口径；数字的当前值不在这里重复维护。

## 为什么做

填写业务场景、使用方、当前痛点和为什么现在需要解决。描述一个具体失败例子，给出 case 或反馈的可访问链接。

## 目标与范围

- 预期获得的算法能力：待填写。
- 输入 / 输出与适用场景：待填写。
- 本次包含的功能或实验范围：待填写。
- 本次不解决的问题：待填写。

## 成功标准

先与 Owner / 使用方确认，再开始优化。每项都有判定条件和证据来源；不要只写“效果好”“交付可用”。

| ID | 维度 | 指标或可检查要求 | baseline / 目标阈值 | 测试口径与预期证据 | 验收人 |
| --- | --- | --- | --- | --- | --- |
| AC-01 | 业务能力 | 待填写：需要支持的场景与功能 | 待填写 | 场景测试或使用方验收记录 | 待填写 |
| AC-02 | 算法效果 | 与 project.yaml.goal 一致 | 待填写 | 固定评测集、原始报告、代码/模型版本 | 待填写 |
| AC-03 | 关键 case | 困难样例或人评通过条件 | 待填写 | 样例集合、抽样和标注口径 | 待填写 |
| AC-04 | 工程效率 | 延迟 / 吞吐 / 显存等 | 待填写 | 硬件、精度、输入、batch、统计方式 | 待填写 |
| AC-05 | 退化约束 | 质量、稳定性或主干 regression | 待填写 | 同口径对照评测 | 待填写 |
| AC-06 | 可复现交付 | 代码、配置、数据、模型和复现方法齐全 | 待填写 | assets.yaml 和 delivery.md | 待填写 |

不适用项保留并说明原因，例如无模型训练的算法没有模型权重，但仍然需要代码、输入样本、配置和结果。阈值对应的详细计算方式写在 [eval.md](eval.md)。

## 阶段与停止条件

当前阶段、每个里程碑的负责人、截止日和证据保存在 `project.yaml.milestones`。在这里说明：

- 最小可行性实验需要回答什么：待填写。
- 什么结果允许进入后续验证或交付：待填写。
- 什么结果会停止该方向或重新定义问题：待填写。
- 时间 / 数据 / 算力预算：待填写。

不强制经历大规模训练；小项目只设置必要的阶段。

## 关键依赖和未知项

列出依赖的资产 ID 或外部仓库、接口要求、接收条件和需要协调的人。当前阻塞放在 `project.yaml.blockers`，历史处理放在 [progress.md](../progress.md)。

## 定义确认与变更

- 目标 / 验收确认人和日期：待填写。
- 最近变更原因和关联 ADR / 检查点：待填写。

变更阈值、范围或评测口径时说明原因及对既有结果的影响，不覆盖旧实验中的判定标准。
